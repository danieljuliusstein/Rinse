Grounding context

Codebase. Automations is a first-party React Flow builder: list hub (templates + workflows) and full-page editor (palette | canvas | inspector). Triggers/actions are closed CRM unions; validateWorkflow rejects unknown kinds; executeActionNode only runs CRM actions that write Activities. POV: first-party spine now, Zapier later as adapter. No Apps catalog or connect-state model exists; Settings only mentions Stripe under invoicing.

Learnings. One transferable constraint from deals-board-teleport-fix: visible UI must match actionable targets — don’t show Slack as runnable if it isn’t.

External. Attio gated blocks (visible when unconnected + Connect CTA); HubSpot app-named picker groups; Zapier embed as long-tail; promote AI as a tier. Keys-later “design first” is common.

Topic axes

  1. A1 Catalog discovery — Apps on the Automations list hub
  2. A2 Canvas & palette placement — how apps become building blocks
  3. A3 Connect & readiness UX — stubs without real OAuth
  4. A4 App taxonomy & priority — 16 tools without a logo dump

I1 · Rank 1

Destination stamps + branded Activity shadows

A2 Canvas & palette · A5 Spine Conf 88% Cx Medium
Description Keep Triggers / Actions / Logic / Templates as today. Do not invent 16 new runnable node kinds. Instead, first-party actions (create_activity, Log note, tags) gain an optional destination stamp in the inspector (Slack, Notion, Stripe, …). Runtime still executes the CRM action; subject/body is branded e.g. [Slack] Deal booked so Contact Activity shows the intended fan-out. OAuth later upgrades stamp → real delivery without rewriting graphs.
Basis direct: closed AutomationAction unions + CRM-only executeActionNode; AutomationNodeData already has open string index for appId; POV Activities-as-hub; learning visible=actionable.
Rationale Ships the marquee promise inside Automations without lying that Slack runs today, and without waiting on the keys plan. Matches the POV that Desk CRM is the integration hub.
Downsides Marketing may want literal Slack nodes; stamps can feel “fake Slack” unless chrome is brutally honest. Inspector must stay clear that the write is an Activity until Connect ships.

CRM spine stays executable; apps are destinations on the Activity write.

I2 · Rank 2

APP_CATALOG / Manifest registry

A4 App taxonomy Conf 90% Cx Low
Description Add a static APP_CATALOG (clone Forms FIELD_CATALOG): id, label, icon, formation (AI / Notify / Money / Sync / Escape), readiness (fielded | liaison | paper), spine roles, and default stamp copy. One registry feeds list hub tiles, palette rows, inspector stamp picker, and later OAuth status.
Basis direct: Forms field catalog + FieldPalette pattern; closed unions make ad-hoc string lists painful; Stripe already appears as settings copy without a registry.
Rationale Makes every future app a data row instead of a type-system change. Encodes taxonomy (AI first, Zapier last) as product policy in code.
Downsides Empty registry with no UI is dead weight — must ship with at least stamps or journeys. Don’t grow enums for each app.
I3 · Rank 3

App-journey templates (Template-to-App Binding)

A1 Catalog discovery Conf 86% Cx Low
Description Don’t lead with a logo wall. Extend the existing “Start from a template” grid with branded journeys: “Form → Slack-ready note”, “Deal booked → Stripe invoice prep”, “Chat → Claude summary note”. Graphs remain CRM-only (or stamp-ready). Unpaired tools (GitHub, Linear, Maps) sit on a secondary “by the glass” rail.
Basis direct: Automations list discovery is already templates + workflows; templates.ts accents form|deal|chat; council push for English templates over jargon.
Rationale Answers “where do the 16 apps live?” on the surface users already use to start work — without inventing a marketplace that can’t connect yet.
Downsides GTM may still want equal logo weight; editorial pairings need ownership or they rot.
I4 · Rank 4

Liaison / Mark-for-connect (honest readiness)

A3 Connect & readiness Conf 85% Cx Low
Description Ban fake “Connect” that implies OAuth. Reuse Settings’ Mobile only / opacity pattern: states Available on spine · Marked for connect · Live (later). CTA opens an Automations sheet: what the app will do, which CRM events it pairs with, “Credentials in a later plan / Notify me.” Stripe’s sheet can deep-link Money / Payments copy.
Basis direct: Settings hub disabled rows with “Mobile only”; POV defers OAuth/Zapier review; user constraint that keys are a separate plan.
Rationale Gives a shippable Connect UX that won’t train users to expect a broken OAuth dance — and queues demand for the credentials plan.
Downsides Less flashy than Attio’s Connect CTA; product language must stay consistent across list + inspector.
I5 · Rank 5

Zapier as the sole foreign adapter node

A4 Taxonomy · A2 Palette Conf 82% Cx Medium
Description Fifteen marquee apps appear as stamps / journeys. One palette item — Zapier / webhook (soon) — is the named long-tail escape hatch: dimmed, inspector shows payload shape (contact_id, trigger, stage…), non-executing until the adapter plan. Avoids treating Zapier as peer to Slack.
Basis direct: POV “Zapier later as adapter, not prerequisite”; external Zapier-embed-node pattern; palette already uses disabled styling for structural unreadiness.
Rationale Keeps the type-system story clean: one foreign concept for the long tail; natives stay spine-first.
Downsides Power users may want Zapier live immediately; dimmed node must not look broken.
I6 · Rank 6

Costume / stub-first app nodes

A2 Canvas & palette Conf 78% Cx High
Description Heavier alternative to stamps: add an Apps palette section; dropping Slack places a branded “fitting” node (dashed border / Fitting chip). Graphs save; validateWorkflow warns fittings don’t run (or they only write Activity receipts). Live CRM actions remain the only performable nodes until OAuth.
Basis external: Attio gated blocks; direct: validateWorkflow already errors unknown action kinds; learning visible=actionable prefers explicit warning over silent skip.
Rationale Best when composition of multi-app chains matters more than honesty-of-spine. Pair with liaison language.
Downsides Touches unions, icons, inspector schemas, runner — higher burden than stamps for the same marketing claim. Prefer I1 unless users must see app-shaped topology.
I7 · Rank 7

Activity Feed as App Connect Inbox

A5 First-party spine Conf 74% Cx Medium
Description Once stamps/shadows write [Slack] / [Stripe] Activities, add an Activities filter + inline “Mark for connect” on those rows. No new Integrations page — the audit spine becomes the demand inbox for the later credentials plan.
Basis direct: Activities already aggregates cross-module events; shadows make subjects filterable; council framed Activity as notification center.
Rationale Compounds I1: every stub run creates visible proof and a queue for OAuth work.
Downsides Depends on I1 shipping first; Activities UI scope creeps if Connect UI is overbuilt here.
